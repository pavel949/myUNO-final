# Sales offers — CO02 / CO07 / AT19 / AT21 / AT28

Authenticated `/ops/sales?spaceId=…` uses the existing `manage_reservations` capability, effective operating-space unit intersection and reservation guest registry. No new roles, calendars, prices, guests or channel sends. Up to four independent unit alternatives, each with its own dates/party; these are alternatives, not a group reservation or inventory lock.

Canonical reuse: `computeCanonicalPriceBreakdown` (integer satang, THB only), `checkAvailability`, source-calendar authority, cancellation resolver, `createBookingAttempt` with its inventory locks/exclusion/idempotency. Live reads and immutable offer snapshots are distinct. Explicit server booking request always uses `instantBook:false`; no checkout/payment or automatic request notification. Existing booking requests do not reserve inventory. Scope and frozen totals are checked again inside the writer lock. Recovery uses the existing booking creation key; no second booking after a lost response.

`SalesTariffValidation` is CONFIGURATION: an independent reviewer must validate the exact `tariffFingerprint`, rule version, evidence, currency, date coverage and expiry. No records are installed by migration; no approval API is exposed. Calculability, existing `taxPolicyVerified`, historical imports and Guide-labelled prices do not constitute review. Synthetic fixtures demonstrate approval; production Layantara remains blocked until its commercial baseline and canonical engine are reconciled separately. Fingerprint covers engine contract, unit/category, offerings/policies, rate plans, dated rules, config defaults and effective scope overrides. Any change invalidates approval. Only THB is supported by the existing canonical engine; no conversion or invented other-currency totals.

`SalesOffer` and `SalesOfferOption` are CANONICAL commercial document history, protected by DB append-only triggers, same-transaction option insertion and deferred 1–4 option-count enforcement, with revision concurrency and command replay. Snapshots are constructed server-side and contain only guest-safe fields; no Net, margins, commission, customer identity/contact, guest lists or private notes. Internal validation/evidence IDs and fingerprints stay staff-side. Client notes are explicitly intended for the client. Staff preview is authenticated. An explicit staff action can issue a high-entropy 32-byte capability for the exact offer revision, expiring no later than the offer. Only its SHA-256 hash is stored. The standalone `/proposal#<capability>` document does not render the application/authenticated shell; it clears the fragment after reading it and exchanges the token in a POST body with credentials omitted. No token appears in server request URLs, analytics, messages, logs or generated artifacts. Capabilities are revocable, expire server-side, and cease working when the issuing staff loses effective scope. Guest DTOs are recursively allowlisted. Images use the existing same-origin Next optimizer and its configured remote-host restrictions; proposal CSP permits only same-origin images, and no client headers are forwarded upstream. Each load/export captures its capability and generation so delayed responses cannot restore or print another proposal. Stale/superseded snapshots remain identifiable with a warning and disabled CTA/export. Revoked/expired links return no snapshot. Print/save PDF and copy text use the same guest projection and revalidate immediately before export. The public CTA opens the existing canonical property/review journey, which requires fresh quote, authentication and consent before any booking write; the capability grants no booking authority. No automatic external sends are implemented.

Reconciliation before adding models: existing `ShareStayOffer` is a non-persisted public estimate text helper; it cannot represent versioned commercial documents. `CrmOpportunity`/`crm.service.ts` provide relationship stages (including `proposal`), not a stay-offer snapshot/writer. Existing `ServiceQuoteRequest`/`ServiceQuoteVersion` belong to service-order negotiation and must not become another stay pricing authority. The new models own only the sales document, independent review evidence and its capability; properties, inventory, CRM identities, pricing, policies and bookings remain with their established writers. Direct CRM-opportunity linking is deferred; canonical guest registration and an immutable booking `sales_offer_reference` provide the first-version handoff.

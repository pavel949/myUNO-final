# Frontend, navigation, content and commerce funnel architecture audit

Date: 2026-10-08 · source baseline `24138a2` on main. Scope: current modular frontend and public discovery → dated search → quote → booking, public services → order, content/localization and readiness for additional destinations. Read-only source assessment against PROJECT.md and canonical ARCHITECTURE/DESIGN/AI_AGENT_RULES. No DB mutation, load test, production command or new runtime claim. Existing separate runtime audit evidence is not substituted for architectural proof.

## Verdict

The modular monolith and shared pricing/authority seams are suitable foundations. The application is presently a Phuket deployment with some destination-configured presentation. It is not yet a safely scoped multi-destination marketplace. Main risks are unbounded search quotation work, duplicated query/orchestration paths, lost service context on login, ambiguous empty/error states and destination defaults that do not propagate consistently through UI, readers and financial contracts.

## Expansion beyond Phuket

`src/modules/destinations/index.ts:16` contains only Phuket. `getDestination` silently maps unknown keys to Phuket at `:34`; `destinationPath` returns unchanged path at `:40`. This is a useful single-deployment presentation facade, not tenant isolation. Search uses destination for metadata/telemetry (`api/search/units/route.ts:42`, `:498`) while actual discovery predicates cover project/area/category only (`public-discovery.ts:22`). Do not connect another destination's inventory until the same destination ID participates in every public inventory, map, service-coverage and availability projection.

Project already has timezone/country/city fields (`prisma/schema.prisma:972`, `:984`, `:986`), while presentation formats hardcode `Asia/Bangkok` (`src/lib/format.ts:15`) and the unit date-picker minimum repeats Bangkok (`src/app/units/[id]/unit-client.tsx:409`). Financial fields/defaults are THB (`prisma/schema.prisma:1194`, `:3039`; search price labels `src/app/search/page.tsx:53`). These assumptions are valid for the current market; changing the name alone would misrepresent currency and date boundaries. Destination configuration must carry property timezone, language policy, currency/minor-unit rules, local emergency/legal/coverage requirements and payment capability. Country expansion requires approved commercial/legal decisions, not a global string replacement.

No schema recommendation here duplicates physical Unit or splits ordinary properties into new databases. Follow canonical shared-store scope and stable identity. Current destinationKey on homepage placements (`prisma/schema.prisma:2228`) scopes editorial slots only; it is not destination membership for canonical assets.

## Prioritized architectural sequence

1. **P0, fix before new-market inventory:** explicit destination membership/resolution, scoped readers/API contracts, property timezone and currency propagation; unknown destination errors instead of silent Phuket fallback. Expand schema compatibly with reviewed backfill/parity, then scope reader cutover.
2. **P1, protect growth:** profile search queries and quote fanout, add bounded concurrency/candidate projections and cache keys including date range, guests, scope, pricing version and freshness. Keep quote/hold/confirm server-authoritative; never reuse stale availability as permission.
3. **P1, complete funnel:** typed search/service context and login-return contracts, shared service-order orchestration, standalone delivery/coverage context, honest per-source failure/partial states.
4. **P2, consolidate presentation:** reuse request-level public-detail reads and scoped content batch/cache, standardize approved-copy fallback/locale policy, eliminate literal EN forms via content layer. Preserve distinct operation density and public editorial composition.

## Verification limits

This report maps code and intended contracts, not observed production data volume, query cost, cache-hit rate, security compliance or complete destination launch readiness. No booking/payment/order was created. Existing integration test filenames are evidence of intended coverage, not execution here. Required follow-up acceptance: realistic inventory-size query plans/load tests, cross-destination leakage tests, timezone boundary cases, scoped quote/booking concurrency, login-return filter/service context tests, network failure/retry and localization review with approved copy.

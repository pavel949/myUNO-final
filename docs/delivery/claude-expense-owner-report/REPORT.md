# Отчёт: расход → приватный чек → отчёт собственника → согласование

Дата: 2026-10-11 · База: `main` `6a980f2` (tree `e08e952…`) · Среда проверок: локальная PostgreSQL **17.10**, синтетические данные, боевых URL в окружении не было.
Статус: **кандидат к приёмке**, не выпущен (merge/deploy/push/PR не выполнялись; production и боевая БД не затрагивались).

## 1. Краткий результат

В изолированной среде работает весь контур:

1. Сотрудник (или участник УК) записывает расход **по конкретному объекту** → один авторитетный ряд в ledger; повтор, потеря ответа и двойной клик возвращают тот же ряд.
2. К расходу прикладывается **приватный чек** (шифруется существующим AES-256-GCM, публичного URL нет, таблица закрыта для Data API в той же миграции).
3. Генерация отчёта кладёт расход ровно один раз в нужный период, с трассировкой до проводки и чека; сторно **гасит** расход (раньше — нет).
4. Согласование проверяет «снимок»: устаревший отчёт (новый расход / сторно / замена чека / смена собственника) отклоняется явно (`409 statement_stale`), его можно пересобрать, если это неподписанный черновик.
5. Собственник видит строки и чек только своего видимого отчёта; получатель определяется самим отчётом.

**Заблокировано / не доведено** — см. разделы 6–7: гонка смены собственника (нужен 1 хунк вне зоны), браузерный E2E, backup/restore-гейт, ряд решений за основателем.

## 3. Карта процесса

`UI /ops/costs, /mc/costs (record-cost-client)` → `POST /api/ledger/record-cost` → `recordManualCost` (+`canWriteUnitExpenses`) → `ledger_entry` (отрицательная сумма в сатангах, дата-день) → **`POST /api/ledger/receipts`** → `attachExpenseReceipt` → `expense_receipt` (шифртекст) → `POST /api/admin/statements/generate` → `collectSnapshotSources` → `owner_statement` + `statement_line_item(ledger_entry_id, expense_receipt_id)` → `PUT …/sign-off` (admin/owner) → `recordStatementSignOff` (блокировка объекта → строка отчёта → `verifyStatementSnapshot`) → `/owner/statements/[id]` → `GET /api/ledger/receipts/[id]` (живая проверка прав). Сторно: `POST /api/admin/ledger/[id]/reverse` → `reverseManualCost`.

Права: `money:record_costs_on_units` (doc 03) + сужение по объекту; чтение чека — оператор с правом на объект либо получатель видимого отчёта, который чек цитирует. CO/AT: CO19 (Period Financial Close); AT06 (повтор с тем же ключом), AT27 (исторические получатели), AT28 (чужие ID через API/SSR/media), AT29 (частично: RU/EN/TH-ключи, клавиатура, сбой сети — компонентные тесты; браузер не проверен).

## 5. Приложение по схеме (общая зона — только предложение)

Файл `02-schema-and-migrations.patch`; три **аддитивных** миграции, порядок обязателен:

1. `20261010070000_manual_cost_integrity` — `ledger_entry`: `manual_cost_key`, `manual_cost_fingerprint`, `reverses_entry_id` (nullable); UNIQUE(автор, ключ), UNIQUE(`reverses_entry_id`), FK RESTRICT; CHECK: пара ключ/отпечаток, нет самосторно, день без времени, ручной расход — отток (<0); триггер неизменяемости ручных/сторно-рядов (менять можно только `statement_id` и FK-`SET NULL`; удалять нельзя). Старые ряды не затрагиваются.
2. `20261010102000_private_expense_receipts` — таблица `expense_receipt` **вместе с** RLS ON и `REVOKE ALL FROM PUBLIC, anon, authenticated` в одном файле (открытого промежутка нет); один текущий чек на расход и один текущий файл на систему (частичные UNIQUE); триггер: замена только через `superseded_at`.
3. `20261010103000_statement_snapshot_lines` — `owner_statement.source_fingerprint/snapshot_hash`; `statement_line_item.ledger_entry_id/expense_receipt_id` + UNIQUE(отчёт, проводка).

Ограничения/совместимость: старый код не ломается (колонки nullable); новый код **требует** все три миграции. Безопасный откат приложения: вернуть прежний код — миграции остаются (аддитивны); откат схемы не нужен. Остаточные риски: роли `anon/authenticated` обязаны существовать в среде (как в CI); ключ `ENCRYPTION_KEY` — тот же, что для PII, не менять; триггер блокирует `UPDATE` суммы/даты ручных рядов — любой не показанный мне ручной скрипт правки таких рядов перестанет работать (это цель). Evidence: replay на пустой PG17, нет дрейфа, 3294 теста.

**Гейты до production (не выполнены, не заявляются):** backup + restore-репетиция; сверка на восстановленной копии, что `ledger_entry`/`statement_line_item` не нарушают новые индексы; совместимость с отдельным Booking/Payment schema-repair (порядок миграций с ним согласовать — таймстемпы моих позже `20261008193000`); запуск `prisma migrate deploy` только после этого.

## 7. Не проверено / открытые решения

**Не проверено:** браузерный E2E (расход → чек → отчёт → owner review; RU/EN/TH; desktop/mobile; клавиатура; обрыв сети) — не выполнен (воркер сессии перезапускался, PG и фоновые процессы теряются; компонентные тесты покрывают клавиатуру, сбой/повтор, пустое состояние, загрузку, RU/EN/TH-ключи есть, но живого рендера нет); мобильная вёрстка; скриншоты не приложены; production/staging runtime; реальные уведомления (не вызывались); нагрузка (шифрование 4 МБ в TEXT — приемлемо, не мерялось); `npm run build` не перезапущен после последних правок, затронувших только тесты.

**Решения основателя / коорд. (реализовано обратимо, помечено):**
1. Знак: ручной расход хранится **отрицательным** (doc 02 §5.3); старые положительные читаются корректно (`abs`). Одна константа `MANUAL_COST_SIGN`.
2. `POST …/reverse` теперь только для четырёх типов ручных расходов (раньше мог «сторнировать» выручку и выплаты).
3. Сторно уже выпущенного отчёта датируется **сегодня** (в текущий период), выпущенный отчёт не переписывается.
4. **Поздний расход в выпущенный период** записывается, но ни в какой отчёт не попадает (`period_already_issued`, форма это говорит). Политика (переносить в следующий период? корректирующий отчёт?) — коммерческое решение, не придумано.
5. Устаревший отчёт вне статуса `draft` пересобрать нельзя (только черновик без подписей; `regenerate:true`). Процесс коррекции для `published/pending_owner_review` не определён — стоп по AI_AGENT_RULES §14.
6. Старые сторно без связи (до миграции) по ID не сопоставимы — остаются в старом виде; backfill на production запрещён заданием.
7. Лимит чека 4 МБ (лимит тела запроса хостинга), тип по содержимому; SVG не принимается.
8. Ссылка собственника на чек работает, пока отчёт виден и он его получатель; после `superseded` чека сохраняется то, что отчёт цитировал.
9. Тексты — RU/EN/TH черновики `needs_review`, ZH — fallback на EN; ревью копирайта не проводилось.

# Architecture and security platform audit

Date: 2026-10-08, Asia/Bangkok. Source baseline: `main 24138a2d717773534d923244a102631987aad641`.

## Conclusion and scope

The platform is a modular monolith with substantial existing correctness machinery: signed sessions, session-derived server-action identity, scoped booking access, SQL booking overlap constraints, canonical transaction writers, migration replay/drift checks, structured redacted error reporting and restore-tested backup workflow code. It should be strengthened incrementally rather than rewritten into services.

The current source does **not** justify an unrestricted production-readiness claim. Important authorization differences remain between generic role checks and managed-unit/department guards. Account recovery, production seed safety, external-feed fetching and operational delivery require remediation or explicit verified configuration.

This pass is read-only plus this report. It did not authenticate as a real user, exploit a production endpoint, read production secrets/PII, migrate, seed or mutate a database. Production deployment was being processed by the coordinating agent; source HEAD is not proof of the deployed SHA. No live authorization or infrastructure configuration is marked verified here.

`audit:inventory` was rerun: **160 pages, 227 handlers (224 API), 22 modules, 115 Prisma models, 90 enums, 77 migrations, 311 test files, zero route collisions**. Automated discovery scanned every API source for mutation/auth and direct Prisma patterns; manual tracing covered shared auth/RBAC, representative pricing/availability, booking/check-in, private access/passport, media, OAuth/recovery, actions, payment webhook and release/monitoring boundaries. It did not exhaustively execute all 224 API contracts. There are 37 API files with direct Prisma mutations by the inspected source pattern; this is a boundary-review locator, not 37 proven vulnerabilities.

## API/module boundaries

Canonical style is a modular monolith. High-risk booking transitions are delegated rather than reimplemented: check-in authorizes the session/resource (`api/bookings/[id]/checkin/route.ts:56`) and executes booking transition plus TM30 creation in one transaction (`:77`). Existing structural transition-wiring and write-access guards are worth preserving.

However, many route handlers still contain persistence orchestration and direct writes. Examples: gallery attachment transaction (`api/admin/units/[id]/media/route.ts:35`), private access instruction upsert (`api/ops/units/[id]/access/route.ts:37`), team role revocation (`api/ops/team/route.ts:86`). These are not automatically unsafe; they are places where state validation, audit/event and authorization contracts can diverge.

Adopt application command/query entry points with an explicit authenticated actor, effective scope/capability, validated input and transaction. Domain services such as pricing override creation (`modules/core/availability.service.ts:339`) validate values but do not authorize an actor; therefore a route-only authorization bug is not caught deeper down. Prefer one trusted authorization boundary at the command seam, with defense-in-depth resource checks, while keeping jobs/admin controlled commands explicit. Do not simply duplicate `can()` everywhere.

## Delivery, migration, testing and monitoring

- Build/install are non-mutating: `package.json:7` generates Prisma/builds content and `:6` generates client only. `vercel.json` deploys main; schema rollout is an explicit separate responsibility. The inspected source cannot prove CI completion is a production deployment prerequisite, branch protection exists, or the live DB is at HEAD.
- CI runs the real migration chain, Supabase-compatible roles, replay/drift/Data API verification, DB-backed tests, production typecheck and build (`.github/workflows/ci.yml:87`–`:145`). Preserve this gate. A local green unit run is not migration proof.
- Integration test reset deletes all application rows and temporarily disables trigger behavior (`src/test/util.ts:45`). `DATABASE_URL_TEST` is mandatory (`:8`) and Vitest isolates the app client (`vitest.config.ts:8`). Explicitly validate the test target cannot equal production; merely naming an env var does not prove isolation. No destructive integration test was run here.
- Structured reportError scrubs content and keys and includes correlation reference (`src/lib/observability.ts:94`, `:221`); safe error response helper exists (`app/libs/errorHandler.ts:33`). Migrate bypasses (SEC09), then prove alerts are delivered and searchable.
- Health checks PostgreSQL availability only (`api/health/route.ts:13`). It is not a readiness check for pricing configuration, jobs, provider connectivity, release drift or data quality. Maintain separate liveness, operational readiness and dependency freshness views.
- Backup restores a dump into scratch before encrypted storage; actual scheduled success, decryption custody, logical data consistency and recovery with payment-side effects still require production evidence. Do not report a tested restore from workflow existence.

## Remediation sequence

1. Prove production has no fixed-password privileged demo account; fence demo seed from production. This is a configuration/account check before any destructive change.
2. Close MC effective-unit pricing/block authority mismatch with one command guard and cross-organization fixtures. Then cover PATCH/DELETE/read/export counterparts.
3. Add account-recovery session revocation and atomic one-time token consumption; verify concurrent requests on isolated PostgreSQL.
4. Harden iCal egress and streaming size limits; test redirect/private-resolution cases without touching real internal endpoints.
5. Standardize error/PII logging, reliable auth email failure handling, channel delivery state and shared throttling.
6. Reconcile and prove live migration/constraints/RLS/default-grants, scheduler health/alerts, independent backup and restore/financial reconciliation.
7. Consolidate duplicate role writers and API command boundaries through measured vertical slices; preserve historical money and existing verified workflow behavior.

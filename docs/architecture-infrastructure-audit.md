Deployment READY establishes deployability, not operational scheduler/backup health. ## Preserve

- Modular monolith and PostgreSQL are appropriate for the present stage. Next UI/API around domain services offers a coherent deployment unit; no measured need for microservice splitting is established.
- Normal install/build generate Prisma client and compile only; explicit migration/drift verification in `.github/workflows/ci.yml:83–111` reproduces the chain in test PostgreSQL, with Supabase roles, before typecheck/build. Keep this separate from production restore.
- `src/lib/prisma.ts` provides one client per warm application module; `resolveDatabaseUrl.ts` caps Supabase pool usage, preserves local URLs and requires SSL. Ten pure connection-resolution tests pass. This is a sensible defensive adaptation, not a substitute for pool utilization metrics and correctly configured host/role.
- Jobs have a shared registry, per-job exception isolation and last-run records (`src/jobs/registry.ts`, `record.ts`). Health exposes never/failed/silent states (`health.ts:31–54`), not just an empty green panel. Existing health tests cover the pure evaluation.
- `.github/workflows/backup.yml:128–226` dumps, restores into disposable PostgreSQL, checks schema/history presence and encrypts before storing a 30-day artifact. This is useful implementation evidence; successful recent run/artifact recovery and measured RPO/RTO were not checked here.
- Booking expiry does not depend only on cron: creation expires stale unit holds inside the allocation transaction (`booking.service.ts:331–337`), while availability excludes expired holds (`:163`, `:217`). Preserve these defensive paths.

## Test evidence and next reliability gates

Pure infrastructure suite: 30 tests in 3 files passed (`jobs/health.test.ts`, `integrations/channel-health.test.ts`, `lib/resolveDatabaseUrl.test.ts`). These do not execute production feeds, distributed overlap, alerts or restores. No live scheduler endpoint was invoked.

Required isolated test scenarios: all/partial iCal failures; failed feed restored on next retry; >100 slow feeds with resumable timeout; concurrent same-job claims from two scheduler sources; exhausted retry/quarantine/replay; webhook outage and delayed incident delivery; full backup restore with domain sums and external payment reconciliation; Vercel instance/pool saturation. Record load cardinality, p95 latency, failure/lag, and actual RPO/RTO rather than a synthetic readiness score.

Shared store and single physical Unit should remain the foundation. Add scope to queries and bounded async execution first; extract services only for measured throughput/ownership reasons. Multi-destination expansion should not multiply scheduler/code/database forks.
